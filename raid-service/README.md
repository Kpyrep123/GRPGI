# Тестовые вылазки v290

Это отдельный серверный режим веб-клиента. Он выключен по умолчанию. Профили настоящие: расход патронов, предметы, прочность, травмы и смерть сохраняются. Перед проверкой нужны резервная копия PocketBase и тестовые персонажи.

## Настройка миссии

1. В редакторе боевой сцены нарисовать полигоны и назначить роли: старт, эвакуация, переход, цель. Для перехода указать ID карты и ID зоны прибытия. Разместить противников из карточек НПС, выбрать тактику и при необходимости группу. Токены игроков в шаблон миссии не включаются.
2. В World Config открыть «Вылазки — тест». Выбрать кампанию, НПС и доступный ему диалог хаба, карты и стартовую карту. Сохранение копирует подготовленные карты и НПС в определение миссии. Правки исходной сцены не меняют сохранённый шаблон: его нужно сохранить заново.
3. Указать общую денежную награду, очки навыков **каждому** выжившему и гарантированные предметы. Настроить цели: уничтожение группы, взаимодействие в зоне, достижение зоны, доставка предмета или удержание зоны заданное число раундов. Произвольные Lua-условия победы и последовательности задач пока не реализованы.
4. Включить режим для кампании после установки worker. Во время окна пятница 20:00 — понедельник 08:00 по Москве сервер выбирает одну миссию из включённых. Выбор фиксируется при первом обращении. Выключение режима закрывает новое лобби, но не прерывает начатую попытку.
5. Игроки открывают соответствующий диалог НПС в хабе и нажимают «Вылазки». Лидер приглашает участников, каждый подтверждает готовность. Сервер проверяет присутствие каждого у НПС и доступность диалога. После старта присоединение и вторая попытка для кампании в эту неделю закрыты.

## Правила попытки

- Постоянный пошаговый режим, включая обыск и передвижение после победы. Ход 60 секунд. Отключение не останавливает время: просроченный ход завершается сервером.
- Броски выполняет сервер; Lua использует существующий sandbox worker. Реакции и запросы выбора ждут игрока 25 секунд с допуском 1,5 секунды. Таймер хода приостановлен на время выбора и выполнения Lua. Сохранённый бросок повторно не перебрасывается при восстановлении задания.
- НПС используют агрессивную, стрелковую, удерживающую или поддерживающую тактику. Они пользуются собственными экземплярами снаряжения, в том числе аберрированными. Пустой магазин перезаряжается при наличии боеприпасов; очередь продолжается до её завершения. При невозможности использовать оружие выбирается второе оружие или безоружная атака.
- Обыск соседнего поверженного противника расходует Действие. Выбираются конкретные предметы и количества. Сохраняются ID экземпляров, модули, аберрации и текущая прочность; проверяется вместимость инвентаря.
- Перенос соседнего союзника расходует Действие, занимает руки и уменьшает скорость вдвое с округлением вниз. Опустить союзника можно бесплатно. Переносимый союзник следует за носителем и не получает отдельного хода.
- Переход требует всю живую команду в зоне; переносимые союзники учитываются. Переход не восстанавливает Действие, Реакцию и перемещение.
- Один персонаж в свой ход запускает эвакуацию из зоны. Остаток текущего раунда не входит в отсчёт: завершаются три следующих полных раунда. Затем находящиеся в зоне извлекаются, остальные погибают. Живой бессознательный или Умирающий в зоне тоже эвакуируется, без автоматического лечения и стабилизации.
- Награда выдаётся только при выполнении обязательных целей. Деньги делятся строго поровну между выжившими; при неделимой сумме сохраняются дробные кредиты. Очки навыков выдаются каждому в указанном количестве. Гарантированные предметы разбираются выжившими по очереди, по одному предмету; можно передать очередь или завершить получение. Невыбранные предметы не выдаются автоматически. Вынесенная добыча сохраняется и при эвакуации без победы.
- Во время попытки сервер блокирует обычные изменения участвующего профиля и его управление в редакторе боевой сцены. Это предотвращает перезапись ресурсов параллельными приложениями. ДМ может завершить зависшую попытку без миссионной награды; уже сохранённые последствия остаются. После освобождения профиля ДМ может изменить его, в том числе воскресить персонажа.

## Сохранение и протокол

`campaigns.RAIDS_V290[campaignId]` содержит `enabled` и массив `missions`. Карты, НПС, зоны, награды и цели сохраняются в шаблоне; каждый запуск получает снимок мира и шаблона.

При старте PocketBase автоматически создаёт SQL-таблицу `grpgi_raids_v290` с ключом `(campaign, week)` и полями `revision`, `status`, `state`. JSON состояния содержит состав группы, очередь, позиции, экземпляры инвентаря, HP, травмы, критическое состояние, таймеры, эвакуацию, награды, Lua-задания, сохранённые броски и ответы. Завершённые попытки остаются в таблице как архив. Автоматическое удаление архивов пока не реализовано. Журнал ограничен 300 строками, квитанции операций — последними 256; постоянных глобальных коллекций удалённых НПС и предметов нет.

Дополнительное поле `combatState093.lua204` имеет `schema:1`, `ownerId`, `resources`, `sourceData`, `modifiers`, `reactionDebt`. Оно добавляется без переименования старых полей; старые профили без него по-прежнему загружаются. Старые активные попытки с `resources204`, `sourceData` и плоскими `modifiers` переводятся в общие поля runtime без повторной выдачи ручных ресурсов.

Профиль получает `raidLock290 = campaignId + '|' + week`. Сохраняются обычные `stats`, `traumaV195`, `dead229`, `combatState093` (в том числе `dead`, `critical`, `conditions`, `ownTurn`, `control`, `loseNextAction`), инвентарь/экземпляры, магазины, деньги и очки. Поля JSON прежних механик не переименованы. После окончания участия блокировка удаляется; последующие тики не перезаписывают уже освобождённый профиль.

Игровой маршрут: `POST /api/grpgi/auth-v212/raids-v290`, существующая индивидуальная сессия. Команды содержат `operationId`, `revision`, `week`; клиент сохраняет незавершённую команду и повторяет её с тем же ID. Сервер сравнивает версию и отпечаток запроса. Состояние и профили изменяются в одной SQL-транзакции. Дубли последних 256 операций не применяются повторно. Worker получает задания по аренде; ответ старой аренды или завершённого задания игнорируется.

## Lua и оставшиеся ограничения

Публичные названия команд существующего Lua API не изменены. Сигнатуры описаны в `LUA_COMBAT_SCRIPTING.md`; данный режим исполняет только перечисленное ниже подмножество общего боевого runtime.

Поддержаны hooks: `OnActionDeclared`, `OnActionFinished`, `OnMoveStart`, `OnMoveStep`, `OnPositionChanged`, `OnRoundEnd`, `OnHealApplied`, `OnConditionChanged`, `OnKnockedDown`, `OnStandUp`, `OnForcedMove`, `OnModifierChanged`, `OnThinkerInterval`, `OnThinkerDestroyed`, `OnUnitEnter`, `OnUnitLeave`, `OnSceneStart`, `OnBattleStart`, `OnTurnStart`, `OnTurnEnd`, `OnRoundStart`, `OnAttackDeclared`, `BeforeRoll`, `BeforeAttackStart`, `BeforeAttackRoll`, `AfterAttackRoll`, `AfterRoll`, `OnAttackResolved`, `OnHit`, `BeforeDamage`, `OnMiss`, `OnTakeDamage`, `OnShotFired`, `OnDamageApplied`, `OnMoveEnd`, `OnAbilityPhaseStart`, `OnAbilityExecuted`.

Автоматизируются `RequestRoll` и числовые запросы бросков; поддержаны пользовательские запросы цели, числа, варианта, подтверждения, списка и точки. Реализованы основные команды урона/лечения, условий, модификаторов, Action/Reaction, ресурсов, заряда/прочности предмета, sourceData, перемещения и вложенной стандартной атаки. Дополнительный Lua-урон не повторяет крит и бонусы основной атаки.

**Режим не обеспечивает полную совместимость со всеми существующими боевыми скриптами.** Скрипты с неподдержанными объявленными hooks отклоняются до старта. Перенесены сохраняемые thinkers/ауры, события пути и действий. Призыв новых сущностей и полный набор механик основного редактора ещё не перенесены. Неизвестная Lua-команда приостанавливает попытку с ошибкой для ДМа. Анализ hooks распознаёт обычные объявления `function HookName(...)`; динамическое объявление обработчиков не поддерживается. Lua-ресурсы и данные источников используют общие функции `combat-lua-v204`: области сброса `turn`, `round`, `battle`, `scene`, `manual` сохраняют свою семантику. В частности, ручной ресурс не восстанавливается при новом запуске или переносе в обычную сцену. Реакция с несколькими единицами ресурса списывается один раз; явное списание скриптом не дублируется автоматическим.

`combatState093.lua204` переносит ресурсы, sourceData, временные модификаторы и долг Реакции через профиль в обычную сцену и обратно. Модификаторы участвуют в расчёте характеристик и в десктопном/веб-профиле; повторное применение одного ID заменяет прежний эффект. Привязка длительности к собственному runtime-ID переназначается новому токену. **Привязки к runtime-ID другого персонажа между разными сценами пока не сопоставляются.** Состояние критического ранения сохраняется в совместимых плоских флагах и `conditions`. Изменение максимального HP ограничивает текущее HP новым максимумом, без урона, травм и лечения. Снижение максимума при окончании эффекта сохраняется в профиле.

### События, области и движение v292

Действие проходит сохраняемые фазы объявления, исполнения и завершения. Неверная команда отклоняется до запуска её Lua-обработчиков. `CancelEvent` на `OnActionDeclared`/`OnMoveStart` отменяет основное действие/перемещение до его расхода; уже выполненные команды самого обработчика сохраняются. Если условия действия изменились во время обработчика, оно проверяется повторно. Завершение отменённого действия не выдаёт `OnActionFinished`.

Путь хранится в `move292` и выполняется шагами. Между шагами разрешаются `OnPositionChanged`, `OnMoveStep` и события входа/выхода из областей. При остановке, опутывании или потере сознания дальнейшие шаги прекращаются. Перезапуск worker продолжает сохранённый путь. Фазы `turnEnd292` разрешают `OnTurnEnd` и `OnRoundEnd` до смены счётчиков и ресурсов следующего хода. Во время обработки этих фаз клиент не предлагает новые действия.

`GetCostMode`, `GetEventScope`, `GetBehavior` и числовые getters способностей исполняются настоящим Lua worker, результаты кешируются в попытке по владельцу/источнику/скрипту. Обработчики с областью `owner` не срабатывают от чужого перемещения; `scene` получает соответствующие события других участников. У реакций с `Can...` условия проверяются в режиме чтения **до** показа вариантов. Выстрел передаёт hooks только соответствующего оружия и боеприпаса; второе оружие не дублирует обычный `OnShotFired`.

`CreateThinker`, `DestroyThinker`, `SetThinkerVision` и данные thinker поддерживаются. Сохраняются форма, позиция/следование за юнитом, участники, период и срок, вход/выход, видимость и перекрытие обзора. Поддержаны стандартные `aura`, `toggle_aura`, `persistent_area`; аура переключается повторной активацией. Для `point`, `area`, `persistent_area` игрок выбирает точку на карте с серверной проверкой дальности. Области отображаются отдельным динамическим слоем SVG, без повторной передачи фона карты. Стационарные области остаются на своей карте; следующие за владельцем переходят вместе с ним. Вне активной карты периодический урон не обрабатывается, срок при этом продолжает отсчитываться по раундам попытки.

Геометрические запросы `FindUnits`, расстояния, видимости, линии огня и достижимости разрешаются сервером и возвращаются в тот же Lua job. До получения ответов команды и стоимость этого запуска не применяются. Это работает и для запросов внутри `Can...`. Лимит — 32 прохода геометрии, 256 активных областей и ограниченная цепочка событий; завершённые области удаляются из активного состояния. Сами области принадлежат попытке и не переносятся в обычную сцену после эвакуации.

В SQL JSON добавлены необязательные `action292`, `move292`, `turnEnd292`, `thinkers292`, `policies292` и сведения о проверке/повторе Lua job. Новая SQL-таблица или ручная миграция не нужны. При отсутствии этих полей старые попытки продолжаются. Серверный манифест дополнен `raid-effects-v292.js`.

Полного равенства с редактором ещё нет: следующими требуют переноса/проверки Инстинкт самосохранения и моральные состояния, стандартные атаки по возможности/Отход, Помощь, управление дронами/устройствами, взаимодействия с объектами карты и оставшиеся боевые hooks. Косметические Lua-команды звука/частиц и предпросмотра не имеют полного визуального паритета. Ссылки на чужие runtime-ID при переносе эффектов между разными сценами остаются ограничением.

Веб-карта использует отдельный SVG-интерфейс и серверный поиск пути с шагом 0,5. Стены/твёрдые препятствия и высотная видимость учитываются, но полное совпадение геометрии всех размеров токенов, сложных ассетов и вариантов укрытий с десктопным редактором не подтверждено. Изометрия не входит в изменение. Карты тестовой версии рассчитаны на НПС из World Config; дроны, отдельные объекты с собственными действиями и сложные скриптовые сущности не перенесены.

Проверены чистые правила, SQL-транзакции через SQLite с адаптерами PocketBase, настоящий Lua sandbox и DOM обоих клиентов. На рабочем PocketBase, в запущенном Electron и в одновременной сессии нескольких живых браузеров проверка ещё не проводилась. Перед реальным прохождением необходим отдельный прогон на копии кампании.

## Установка сервера

Одной кнопки Deploy Web недостаточно: нужны обновлённые hooks и отдельный Node worker. Команды ниже выполняются из корня репозитория в Bash после получения этой ветки. Существующий каталог `pb_hooks` целиком не заменять.

```bash
node tools/build-loot-core-v137.cjs
node tools/build-raid-core-v290.cjs
ssh -i ~/.ssh/grpgi_deploy root@161.104.35.195 'systemctl show pocketbase -p User -p Group; node --version; mkdir -p /opt/grpgi-raids/raid-service'
```

Нужен Node.js 22 или новее. Проверьте пользователя PocketBase: шаблон нового сервиса использует `pocketbase:pocketbase`; если сервер настроен иначе, исправьте `User` и `Group` в копируемом service-файле. До обновления остановить PocketBase и сделать резервную копию его `pb_data` и `pb_hooks` штатным способом. Затем загрузить файлы:

```bash
while IFS= read -r file; do
  scp -i ~/.ssh/grpgi_deploy "pocketbase/pb_hooks/$file" root@161.104.35.195:/opt/pocketbase/pb_hooks/
done < raid-service/hooks-v290.txt
scp -i ~/.ssh/grpgi_deploy lua-sandbox-worker.cjs root@161.104.35.195:/opt/grpgi-raids/
scp -i ~/.ssh/grpgi_deploy raid-service/worker.cjs root@161.104.35.195:/opt/grpgi-raids/raid-service/
scp -i ~/.ssh/grpgi_deploy raid-service/package.json root@161.104.35.195:/opt/grpgi-raids/package.json
scp -i ~/.ssh/grpgi_deploy raid-service/grpgi-raids.service root@161.104.35.195:/etc/systemd/system/
```

Манифест включает общие зависимости из репозитория, необходимые для запуска. Ручные правки соответствующих серверных файлов нужно предварительно сопоставить с веткой. Остальные установленные hooks сохраняются.

Следующие команды выполняются на сервере. Один секрет используют и PocketBase, и worker. Он не передаётся в веб-клиент и не хранится в World Config:

```bash
npm install --prefix /opt/grpgi-raids --omit=dev
umask 077
RAID_WORKER_SECRET=$(openssl rand -hex 32)
printf 'POCKETBASE_URL=http://127.0.0.1:8090\nGRPGI_RAID_WORKER_TOKEN=%s\n' "$RAID_WORKER_SECRET" > /etc/grpgi-raids.env
unset RAID_WORKER_SECRET
mkdir -p /etc/systemd/system/pocketbase.service.d
printf '[Service]\nEnvironmentFile=/etc/grpgi-raids.env\n' > /etc/systemd/system/pocketbase.service.d/raids-v290.conf
systemctl daemon-reload
systemctl restart pocketbase
systemctl enable --now grpgi-raids
systemctl is-active pocketbase grpgi-raids
journalctl -u grpgi-raids -n 30 --no-pager
```

При повторной установке сохранять существующий `/etc/grpgi-raids.env`, новый секрет не генерировать без одновременного перезапуска обоих сервисов. Затем выполнить обычный Deploy Web и обновить десктопный клиент. Проверить лобби и старт на тестовых профилях: без heartbeat worker сервер не разрешит старт и не заблокирует профили.

При отказе worker часы игрока не обрабатываются до его возвращения; после восстановления просроченные ходы завершаются. Не отключать hooks при активной попытке: сначала завершить её командой ДМа и убедиться, что `raidLock290` снят.
