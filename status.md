# GRPGI — актуальное состояние и инструкции

Обновлено: 2026-11-24. Основа: `main` репозитория `Kpyrep123/GRPGI`, включая синхронизацию v300–v308. Это рабочая сводка, а не журнал патчей. История изменений доступна через `git log -- status.md` и PR; завершённые исправления сюда повторно не добавлять.

## Обязательный принцип сохранения

**Сохранять, передавать и применять минимальный затронутый набор данных. Изменение одной сущности не должно запускать полное сохранение и повторную загрузку всей кампании.** Применять этот принцип к новым и перерабатываемым путям; оставшиеся старые полные операции перечислены ниже как технический долг.

1. **Выбирать правильное хранилище.** Инвентарь и профиль изменять через существующую версионную синхронизацию `campaign_players`. Сообщения используют `campaign_messages`, боевой runtime — свой канал. Не заменять эти пути записью общего снимка кампании. Справочники мира сохранять по затронутым разделам и передавать изменёнными документами.
2. **Явно задавать область изменения.** Для локальной записи использовать `saveWorldSections`, для отправки — соответствующие `worldSections`/`worldScope`. При смене ID, удалении и изменении ссылок включать действительно затронутые разделы. Обычная правка каталога не имеет права публиковать локальные часы, сообщения и прочее игровое состояние. Правка персонажа в World Config включает `players` и связанных `state.users`, сохраняя остальные серверные данные.
3. **Сначала надёжно сохранить намерение.** Локальное изменение сохранять до отправки; для изменений мира использовать существующий долговечный журнал ожидающей операции. Сохранять действующие очереди, атомарную запись файлов, ID операции и проверки ожидаемых версий. Не создавать параллельный механизм сохранения рядом с ними. Журнал одной неопределённой отправки не считать готовой очередью произвольных офлайн-правок.
4. **Различать локальную запись и подтверждение сервера.** `pending` — ожидание, а не успех и не доказательство отмены. После тайм-аута проверить квитанцию и получить канонические данные. Не запускать новую операцию с другим ID взамен неопределённой. Явный повтор использует прежние ID и тело запроса, включая восстановление после перезапуска.
5. **Не терять чужие и более свежие правки.** Сравнивать намерение с исходной базой редактора. Сохранять проверки версий сущностей, права ДМа, серверные защиты целостности и атомарность снимка/индекса/квитанции. Свежая проверка служебного маркера не даёт права обходить конфликт данных персонажа. Более новый локальный черновик нельзя перезаписать старым подтверждением.
6. **Различать увиденную и применённую ревизии.** Метаданные ping, отказа и пропущенного pull обновляют наблюдаемую ревизию. Применённую ревизию, токен базы и базу сравнения повышать только после успешного сохранения и применения подтверждённых данных. Ошибка или отложенное применение их не повышает. Все обёртки `applyRemoteSnapshot` обязаны передавать `payload`, `remoteMeta` и `options` без потери аргументов.
7. **Применять обновление один раз.** Сериализовать проверки и применения, объединять одинаковые одновременные проверки. Учитывать фактические изменения данных: старый SQL-путь может изменить снимок без повышения `revision`. База сравнения мира принадлежит серверу/кампании/таблице/ID снимка и переживает вход `guest → gm`; защита выполняемой операции отдельно принадлежит пользовательскому контексту.
8. **Использовать канонический ответ.** Сохранять только изменённые разделы и использовать нормализованные данные ответа записи. Не перечитывать сразу после этого все файлы и состояние. После собственной квитанции применять серверный результат затронутых разделов даже тогда, когда сервер вернул прежнее значение вместо локального изменения.
9. **Сохранять отзывчивость интерфейса.** Не копировать и не нормализовать весь мир ради одной правки без необходимости. Выполнять один финальный рендер затронутого интерфейса. Сохранять черновики, фокус, прокрутку, чаты, отметки прочтения, актуальные профильные записи и локальные боевые сцены. Обновление профиля, пришедшее во время записи, остаётся авторитетным.
10. **Полный путь оставлять для восстановления.** Первое/принудительное получение, смена удалённого мира и неподдерживаемые старые формы могут использовать полное применение. Не превращать этот запасной путь в стандарт для обычного сохранения. Не загружать встроенный мир установщика поверх существующей облачной кампании.
11. **Медиа обрабатывать отдельно.** Выбранное изображение загружается один раз и далее используется по облачной ссылке. Локальное сохранение и обычная синхронизация не должны заново загружать все изображения мира.
12. **Проверять поведение целиком.** Для изменений синхронизации проверять настоящую цепочку обработчиков, включая ошибку записи, потерю ответа после commit, повтор операции, конфликт, новый черновик во время ожидания, вход и смену кампании. Подмена `applyRemoteSnapshot` не проверяет его обёртки. Ускорение подтверждать замерами; не отключать защиты и не считать увеличение тайм-аута оптимизацией.

## Текущая архитектура

| Данные | Текущее устройство |
|---|---|
| Мир / World Config | Локальные JSON-разделы; транспорт изменений сущностей с курсором, версиями и квитанциями. На сервере `campaign_snapshots` пока остаётся совместимой полной копией, а SQL-таблицы синхронизации — индексом изменений. |
| Профили и инвентарь | Отдельные записи `campaign_players`, очереди частичных операций и защита конфликтов. Это действующий быстрый путь, его сохранять. |
| Чаты и бой | Сообщения — `campaign_messages`; общий боевой runtime — `campaign_combat_runtime`. Полные карты и редактор боевых сцен остаются локальными; общий снимок не является автоматической публикацией этих сцен. |
| Неопределённая отправка | Долговечный журнал `sync-pending-v303`, разделённый по подключению/кампании/персонажу; проверка квитанции и получение канонического результата. |
| Индекс мира | Отпечатки разделов позволяют переиспользовать неизменившиеся документы. Индекс строится по фактически сохранённому снимку, включая изменения серверных обработчиков и старые SQL-записи. |

Основные исходники: `main.js` и `preload.js` — Electron/IPC; `renderer/` — desktop; `deploy/site/app/` — веб и источник мобильного клиента; `mobile/` — Capacitor; `pocketbase/pb_hooks/` — серверные обработчики. Базовая версия установщика берётся из `package.json`; номера отдельных модулей не считать версией всего приложения.

## Действующие подсистемы и ограничения

- **Мир и персонажи:** редактор справочников, импорт/экспорт, видимость, избранное, навыки и выдачи от происхождения/профессии. Сохранять ссылки и данные выданных навыков/предметов при редактировании. Стартовые предметы не должны появляться повторно после расходования.
- **Хаб:** редактор карт, непрерывное перемещение, стены/препятствия, туман войны, переходы, диалоги, ящики и торговцы. Изменения редактора остаются в черновике до сохранения; ошибка записи не закрывает и не уничтожает черновик.
- **Снаряжение:** инвентарь, отдельные экземпляры, прочность, модули, аберрации и кузница. При передаче сохранять ID и состояние экземпляра; копирование создаёт независимые ID. Редактирование заготовки кузницы не изменяет уже выданные вещи.
- **Боевые сцены и Lua:** локальный редактор, отдельные ресурсы действий/реакций/движения, состояния, устройства, журнал и второй экран. Общие расчёты и API должны сохранять совместимость между ручными действиями, Lua и серверными сценариями. Отдельные навыки ещё требуют проверки и автоматизации; наличие API не подтверждает работу всех навыков.
- **Биржа и GalaGram:** действующие отдельные торговые операции, заявки/закрытие позиций, режим риска под управлением ДМа, новости и сообщения. Изменение справочника не должно откатывать портфель, баланс или инвентарь игроков.
- **Множественный выбор:** соблюдать [AGENTS.md](AGENTS.md): общий `checkbox-picker-v172`, поиск и чекбоксы; новые теги остаются в черновике, ссылки выбираются из существующих сущностей. Общие desktop/web-модули держать согласованными.

### Отключённые механики

- **Вылазки приостановлены по решению пользователя.** Их UI, вход из диалогов, фоновые опросы и игровой серверный цикл отключены. `grpgi-raids` должен оставаться остановленным и отключённым. Не возвращать кнопки, worker или выполнение движка без нового явного задания. Миссии, снимки, таблицы и сохранённые результаты сохраняются; при отключении не пересчитывать HP, имущество или смерть персонажей.
- **Паника, Инстинкт самосохранения и Потрясение удалены** из обычного боя и вылазок. Не восстанавливать их по старым планам. Совместимые `IsShaken()`/`IsPanicked()` возвращают `false`; это не отменяет травмы, критическое состояние и ошеломление от взрыва.
- **Старая региональная симуляция кораблей/ракет/радаров отключена.** Её JSON сохраняется для совместимости и резервных копий. Не удалять данные старых кампаний и не включать симуляцию при обычной загрузке мира.

## Оставшаяся работа

**Оптимизация приостановлена пользователем. Следующие пункты — сохранённый план, а не команда продолжать реализацию.**

1. Разделить клиентские замеры нормализации мира, состояния и рендера. При секционной записи граф `applyWorldData` пока пересчитывается целиком.
2. Перевести оставшуюся полную локальную запись при редактировании персонажа на ограниченный набор разделов. Не ухудшать существующую профильную синхронизацию.
3. Сократить серверную сборку и сохранение полного снимка. Отдельное основное хранение сущностей ещё не внедрено; текущий индекс не заменяет `campaign_snapshots`.
4. Продолжить проверку навыков и боевых событий по актуальным согласованным правилам после отдельной постановки задачи. Не использовать старые поэтапные планы как доказательство незавершённости уже исправленных механик.

Последняя ручная проверка 2026-11-24: обычное обновление персонажа применено один раз в `mode: sections`, записан только `players` за **118 мс**, вся клиентская цепочка заняла **2158 мс**, серверный `saveSnapshotMs` — **5877 мс**. Это замеры конкретной операции, не гарантии для любых данных и устройств. В `saveSnapshotMs` входят обработчики; `authCleanMs` и `downstreamMs` вложены в него, их нельзя суммировать с ним или называть чистым временем SQLite.

## Проверки и обновление

- Основной набор: `npm run test:pr`. Для синхронизации особенно важны `tests/world-sync-v300.cjs`, `tests/world-sync-v301.cjs`, `tests/world-index-v305.cjs`, `tests/sync-revisions-v303.dom.mjs`, `tests/sync-apply-v304.dom.mjs`, `tests/sync-apply-v307.dom.mjs` и `tests/sync-realtime-v303.cjs`. DOM/SQLite-стенд не заменяет проверку установленного приложения и рабочего сервера.
- Изменение только документации не требует сборки и полного прогона кода. Для общих модулей использовать `npm run check:shared`; для изменённых файлов — подходящие проверки и `git diff --check`. Не заявлять проверенными платформы и сценарии, которые не запускались.
- После слияния обновлять исходники через `git pull` и перезапускать приложение. Deploy Web требуется для изменений веб-клиента; установщик/мобильная сборка публикуются отдельно. Смена клиента сама по себе не устанавливает серверные hooks.
- Для серверных изменений перечислять конкретные файлы, команды обновления и отката. Не заменять каталог `pb_hooks` целиком: на рабочем сервере есть обработчики, отсутствующие в репозитории. Не менять порты/службы по старым патчам и не запускать отключённый worker. Состояние рабочего сервера подтверждать его конфигурацией и журналом.
- Поддерживать этот файл как текущую сводку: заменять устаревшее описание, сохранять обязательные ограничения и открытые задачи. Не накапливать номера слитых PR, старые ветки, повторные таблицы тестов и инструкции выпуска прошлых версий.
