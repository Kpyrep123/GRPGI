# Синхронизация v301 — этап 2, восстановление v303, индекс v305

Приложение и сайт получают изменения мира по курсору. Приложение отправляет изменённые записи с ожидаемыми версиями. Полный исходный снапшот пока остаётся серверной копией для существующих модулей.

## Обновление v305: индекс разделов и измерение сохранения

Этот шаг меняет только серверные обработчики. После слияния выполнить из корня локального репозитория в PowerShell, заменив SSH_USER и SERVER_HOST своими значениями. При ошибке копирования не продолжать до её устранения.

```powershell
git pull
$SyncServer = "SSH_USER@SERVER_HOST"
ssh $SyncServer "systemctl stop pocketbase && mkdir -p /opt/pocketbase/hook-backups-v305 && cp -n /opt/pocketbase/pb_hooks/grpgi_world_sync_v301.js /opt/pocketbase/pb_hooks/grpgi_auth_v212.js /opt/pocketbase/hook-backups-v305/"
scp pocketbase/pb_hooks/grpgi_world_sync_v301.js pocketbase/pb_hooks/grpgi_auth_v212.js "${SyncServer}:/opt/pocketbase/pb_hooks/"
ssh $SyncServer "systemctl start pocketbase && systemctl status pocketbase --no-pager"
```

Перезапуск приложения, Deploy Web, изменение порта и worker для этого PR не требуются. `grpgi-raids` остаётся отключённым. Существующие обработчики целостности сохраняются. Внутренняя SQL-таблица `grpgi_world_sections_v305` и триггер её очистки создаются автоматически; вручную менять коллекции не нужно.

После перезапуска первый запрос строит отпечатки всех разделов. При последующих изменениях индексатор сравнивает SHA-256 фактически сохранённых разделов `world` и `state`. Для неизменившихся разделов используются существующие документы; только изменённые проходят очистку и упаковку. SQL-изменения старых модулей по-прежнему учитываются, даже без повышения ревизии. Отпечатки, версии, снимок и квитанция находятся в одной транзакции; удаление/пересоздание кампании очищает отпечатки. В отпечатках не хранится исходный JSON или пароли.

Этот этап всё ещё читает/разбирает полный снимок, вычисляет отпечатки и читает индекс. Он не переводит основное хранение на отдельные сущности и не устраняет `WORLD_SAVE_ALL` на клиенте. При изменении снаряжения его раздел пока упаковывается целиком, остальные неизменившиеся разделы переиспользуются. Ускорение на рабочем сервере нужно измерить; отдельного заявления об устранении задержки `saveSnapshotMs` нет.

### Что проверить после установки

Сохранить предмет дважды: первая операция после обновления может дополнительно обновить отпечатки из-за удаления старых секретных полей или порядка ключей. В `SYNC_RECOVERED_OPERATION.serverTimings` появятся:

- `prepareSnapshotMs` — подготовка JSON-полей записи до сохранения;
- `indexAfter.loadParseMs`, `readIndexMs`, `planMs`, `writeIndexMs` — чтение/разбор снимка, чтение индекса, подготовка изменений, запись индекса;
- `indexAfter.packedSections`, `reusedSections`, `writtenDocuments` — сколько разделов упаковано/переиспользовано и сколько документов действительно изменено.

Длительные вызовы обработчика авторизации (от 100 мс) выводят строку `[GRPGI snapshot timing v305]`:

```powershell
ssh $SyncServer "journalctl -u pocketbase --since '5 minutes ago' --no-pager"
```

`authCleanMs` — очистка `worldJson/stateJson` в обработчике авторизации; `downstreamMs` — последующие обработчики и операция БД внутри `e.next()`. Эти интервалы вложены в `saveSnapshotMs`, складывать их с ним нельзя. Это ещё не отдельные замеры старого обработчика целостности и чистой записи SQLite. Журнал содержит только идентификатор кампании, ревизию, длительности и признак ошибки; содержимое сущностей и текст ошибок не выводятся.

Откат серверного кода:

```powershell
ssh $SyncServer "systemctl stop pocketbase && cp /opt/pocketbase/hook-backups-v305/grpgi_world_sync_v301.js /opt/pocketbase/hook-backups-v305/grpgi_auth_v212.js /opt/pocketbase/pb_hooks/ && systemctl start pocketbase"
```

Дополнительная таблица содержит только восстанавливаемый индекс. Старый код её игнорирует; вручную удалять таблицы для отката не требуется.

## Установка после слияния PR

Выполнить из корня репозитория в PowerShell. Заменить SSH_USER и SERVER_HOST на свою учётную запись и адрес; нужны права управления сервисом и записи в каталог hooks. При ошибке копирования не продолжать до её устранения.

```powershell
git pull
$SyncServer = "SSH_USER@SERVER_HOST"

ssh $SyncServer "systemctl stop pocketbase"

scp pocketbase/pb_hooks/world-sync-v301.js pocketbase/pb_hooks/grpgi_world_sync_v301.js pocketbase/pb_hooks/grpgi_world_sync_v301.pb.js "${SyncServer}:/opt/pocketbase/pb_hooks/"

ssh $SyncServer "systemctl start pocketbase && systemctl status pocketbase --no-pager"
ssh $SyncServer "journalctl -u pocketbase -n 40 --no-pager"
```

Затем обычный Deploy Web, обновление страниц игроков и обновление/перезапуск приложения. Порт не меняется. Новые процессы, npm-зависимости и настройка worker не нужны. Сервис `grpgi-raids` остаётся отключённым.

Нужен уже установленный `grpgi_auth_v212.js` с авторизацией персонажей. Каталог pb_hooks целиком не заменять: новые файлы добавляются рядом с существующими. Три внутренние SQL-таблицы и три триггера создаются автоматически, вручную менять коллекции не требуется. На первом запросе индексируется существующий снимок; последующие запросы передают изменения. Старые клиенты продолжают читать обычный снимок.

Если обновлённый клиент работает со старым сервером, 404 нового маршрута включает прежнюю синхронизацию до следующего входа/перезапуска. Поэтому работа клиента сама по себе не подтверждает установку нового обработчика. В сетевых запросах сайта после входа должны появиться `POST /api/grpgi/auth-v212/world-v301/pull` с ответом `schema: 301`. При повторном запросе без изменений `changes` пуст. Ошибки авторизации и временные ошибки сервера не переключают запись на старый путь.

## Гарантии протокола

- Записи имеют собственные версии и возрастающий номер изменения. Удаления сохраняются, чтобы выключенный клиент получил их при возвращении.
- Контейнеры и порядок списков представлены отдельно. Существующие каталоги и их списки восстанавливаются в прежний формат без изменения редакторов.
- Запись требует действующей сессии ДМа своей кампании и права обновления снапшота. Чтение требует сессии своей кампании и права просмотра.
- Все ожидаемые версии проверяются до сохранения. При конфликте изменения не применяются частично.
- Локальные намерения сравниваются с исходной ревизией, а не с только что полученными данными. Изменения разных записей сохраняются вместе; конфликт одной записи возвращается пользователю.
- Снапшот, индекс и квитанция операции записываются одной транзакцией. Повтор ID с теми же изменениями не исполняет запись заново; с другими изменениями отклоняется.
- SQL-триггеры учитывают изменения через старые модули, в том числе SQL без увеличения ревизии. Чтение неизменившегося индекса не захватывает writer.
- Epoch сбрасывает старый курсор при удалении и пересоздании кампании. Принудительная загрузка в приложении пересоздаёт транспортный baseline.

## Неизвестный результат отправки (v303)

Клиентский timeout не отменяет серверную транзакцию. Перед отправкой приложение сохраняет исходный ID и изменения в атомарном локальном журнале `sync-pending-v303`. Токен сессии туда не записывается. Не удалять журнал вручную, пока результат не выяснен.

Форма World Config не ждёт завершения серверной транзакции: после локальной записи и постановки в журнал передача выполняется в фоне. Метка ожидания отличается от подтверждённой синхронизации. Обработчики целостности на сервере выполняются полностью. Realtime-подключение сохраняется при повторном чтении неизменённых настроек.

В состоянии «ожидается подтверждение» обычные проверки запрашивают квитанцию операции. Если запись подтверждена, клиент получает свежие данные. Если квитанции ещё нет, результат остаётся неопределённым; новые операции не отправляются. В разделе синхронизации кнопка «ПОВТОРИТЬ ОЖИДАЮЩУЮ ОТПРАВКУ» сначала проверяет статус и при необходимости отправляет ту же операцию. Идемпотентный сервер не применяет один ID дважды. Журнал сохраняется между перезапусками и входами тем же персонажем.

Серверные замеры хранятся в квитанции. В терминале приложения после восстановления появляется `SYNC_RECOVERED_OPERATION` с `serverTimings`. Поля `writerWaitMs`, `indexBeforeMs`, `saveSnapshotMs`, `indexAfterMs` отделяют ожидание SQLite, индексирование и сохранение снапшота с установленными hooks. Замер `saveSnapshotMs` включает обработчики целостности; они не отключаются.

Это не полная офлайн-очередь. При ожидании результата текущая форма остаётся черновиком; её новая отправка откладывается до подтверждения предыдущей. Реальная скорость сервера ещё требует проверки.

## Проверка

```text
node tests/world-sync-v301.cjs
node tests/world-sync-v301.dom.mjs
npm run test:pr
```

Первый тест исполняет серверные маршруты над реальной SQLite с адаптером PocketBase API. Второй исполняет функции сайта в DOM. Они не заменяют проверку установленного бинарного PocketBase и реальной нагрузки сервера.

Проверить в приложении редактирование и удаление тестового предмета, появление результата на сайте, повторную загрузку после разрыва связи и сохранность кузницы, карт и инвентаря. В тестовом каталоге из 600 предметов редактирование одной записи передаёт сам предмет и его запись в совместимом списке; размер запроса меньше 1% полного снимка. Это измерение тестового сценария, а не ускорение живого приложения.

## Оставшаяся работа

Транспортный кеш пока находится в памяти процесса/страницы. После перезапуска первый запрос полный. Сборка мира и сравнение документов ещё выполняются целиком; редакторы и применение полученных данных частично используют прежний общий путь. Сервер для совместимости обновляет полный снапшот и сверяет индекс при его изменении. Инвентарь использует прежний отдельный протокол.

Следующий этап: постоянный локальный кеш, сохраняемая очередь отправки, запись и применение отдельных сущностей без общей пересборки. Оптимизация Lua и смены ходов выполняется после синхронизации. Дополнительный сервер не требуется.
